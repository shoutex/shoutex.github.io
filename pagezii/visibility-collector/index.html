Phase 1: building the AI visibility collector

Phase 1 answers one question reliably: how often is a brand mentioned, recommended or cited across AI engines for a fixed set of prompts? Here is the collection method, the data model, the parsers and the metric queries.

ShoutEx Team · Updated October 2026 · Page 2 of 4
Pagezii roadmap / Phase 1: Visibility collector

How should answers be collected from each engine?

Collect through official APIs with web search or grounding turned on, never by scraping consumer chat interfaces. APIs are stable, legal to automate and return citations as structured data. OpenAI's web search tool, Gemini's grounding with Google Search and Perplexity's search API each return the answer text plus the sources used.

pythonfrom openai import OpenAI

client = OpenAI()

def collect_openai(prompt: str, model: str) -> dict:
    resp = client.responses.create(
        model=model,                       # pin and record the exact model
        tools=[{"type": "web_search"}],    # check the docs for the current tool name
        input=prompt,
    )
    citations = [
        ann.url
        for item in resp.output if item.type == "message"
        for part in item.content
        for ann in (getattr(part, "annotations", None) or [])
        if ann.type == "url_citation"
    ]
    return {"engine": "openai", "model": model,
            "answer": resp.output_text, "citations": citations,
            "raw": resp.model_dump()}
pythonfrom google import genai
from google.genai import types

gclient = genai.Client()

def collect_gemini(prompt: str, model: str) -> dict:
    resp = gclient.models.generate_content(
        model=model,
        contents=prompt,
        config=types.GenerateContentConfig(
            tools=[types.Tool(google_search=types.GoogleSearch())]),
    )
    meta = resp.candidates[0].grounding_metadata
    citations = [c.web.uri for c in (meta.grounding_chunks or []) if c.web]
    return {"engine": "gemini", "model": model,
            "answer": resp.text, "citations": citations,
            "raw": resp.model_dump()}
Important

API answers are not identical to what a signed-in user sees in the consumer app, which can add memory, location and personalization. Report Pagezii's numbers as API-measured visibility and say so on every chart.

How many times should each prompt be run?

Run every prompt several times per engine per collection cycle, because AI answers vary between identical requests. A single run tells you what one answer said; five to ten runs tell you how often a brand appears. Store each run with a sample number so variance can be measured, and keep temperature and model settings fixed within a cycle.

Budget this early. Prompts multiplied by engines, samples and weekly cycles grows fast, so start with a few hundred prompts and expand only when the metrics are stable.

What does the data model look like?

Five core tables cover Phase 1. Raw answers live in JSONB so nothing is lost; parsed rows are derived and can be rebuilt at any time.

sqlcreate table brands (
  id        serial primary key,
  name      text not null,
  aliases   text[] not null default '{}'   -- "HubSpot", "Hubspot CRM", ...
);

create table prompts (
  id        serial primary key,
  text      text not null,
  intent    text,                          -- set in Phase 2
  locale    text not null default 'en-CA'
);

create table runs (
  id          bigserial primary key,
  prompt_id   int references prompts(id),
  engine      text not null,               -- openai | gemini | perplexity
  model       text not null,
  sample_no   smallint not null,
  run_at      timestamptz not null default now(),
  answer_text text not null,
  raw         jsonb not null
);

create table mentions (
  run_id      bigint references runs(id),
  brand_id    int references brands(id),
  first_pos   int,                         -- character offset of first mention
  recommended boolean,                     -- set by the LLM judge
  primary key (run_id, brand_id)
);

create table citations (
  run_id  bigint references runs(id),
  url     text not null,
  domain  text not null,
  rank    smallint                         -- order in the source list
);

How are brand mentions and recommendations detected?

Use two passes. First, deterministic alias matching with word boundaries finds every mention and its position; it is fast, cheap and easy to test. Second, an LLM judge with a structured output schema decides whether each mentioned brand was actually recommended, merely listed or warned against. Validate the judge against a hand-labelled sample of a few hundred answers and track its precision and recall like any other model.

pythonimport re

def find_mentions(answer: str, brands: list[dict]) -> list[dict]:
    hits = []
    for b in brands:
        names = [b["name"], *b["aliases"]]
        pattern = r"\b(" + "|".join(map(re.escape, names)) + r")\b"
        m = re.search(pattern, answer, flags=re.IGNORECASE)
        if m:
            hits.append({"brand_id": b["id"], "first_pos": m.start()})
    return sorted(hits, key=lambda h: h["first_pos"])
CTO rule

Test the parser like production code.

A mention rate is only as good as the parser behind it. Keep a labelled test set in the repository and fail the build when precision or recall drops.

Which metrics come out of Phase 1?

Three metrics are enough for a first release: mention rate (share of runs that mention the brand), recommendation rate (share of runs where the judge marks it recommended) and citation share (share of cited URLs on the brand's domains). Pagezii's note on what AI visibility is and why it differs from SEO rankings explains why these replace rank as the core unit.

sql-- Weekly mention rate per engine for one brand
select date_trunc('week', r.run_at) as week,
       r.engine,
       avg((m.brand_id is not null)::int)::numeric(5,3) as mention_rate,
       count(*)                                        as runs
from runs r
left join mentions m on m.run_id = r.id and m.brand_id = :brand_id
group by 1, 2
order by 1, 2;
